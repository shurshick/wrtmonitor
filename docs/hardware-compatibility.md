# Совместимость оборудования

Поддержка функции определяется capability и наблюдаемым состоянием, а не названием модели. Каталог SoC/датчиков помогает объяснять telemetry, но не является сертификатом поддержки.

## Confirmed hardware: исторические hardware E2E

Источники: [Netis](../certification/netis-nx31.json), [x86](../certification/openwrt-x86.json). Для каждой команды в этих отчётах записаны pass / unsupported, повторная доставка, timeout и post-condition. Группы: agent, diagnostics, network/DHCP/DNS, clients, firewall, VPN, system/maintenance; Wi-Fi проверялся только на Netis. Полная command-by-command область указана в JSON, а текущие требования capability - в [Supported Features](supported-features.md).

Не переносить эти результаты автоматически на новый backend или агент. Короткая проверка Netis 2026-10-04 на установленной 0.55.4 подтверждает связь и Web SSH, но не полный E2E 0.55.5 или кандидата 1.0. x86 тогда был offline. Перед 1.0 нужен полный hardware E2E точного кандидата минимум на одном физическом роутере.

## Expected compatible

Другие OpenWrt-устройства с UCI, ubus, procd, доступным apk/opkg, корректными package feeds и исходящим HTTPS ожидаются совместимыми с базовым агентом. Это не обещание работы конкретной модели, архитектуры или всей command matrix. Требования установки: [OpenWrt Agent](openwrt-agent.md).

Новая модель может автоматически появиться как наблюдаемый профиль. `origin=observed` и `verified=false` не означают аппаратную сертификацию. Частоты, температуры и пороги показываются только при наличии данных ядра; отсутствующие датчики означают unsupported, а не нулевую температуру.

## Unsupported / unknown

Без radio PHY нет Wi-Fi-форм; без нужного пакета/модуля скрываются соответствующие операции. Unknown, stale и error нельзя выдавать за поддержку или успех команды. Неизвестная модель не блокирует весь UI, но не включает отсутствующие возможности. Неподдерживаемая прошивка/образ не разрешается только по совпадению имени модели.

## Как добавить оборудование

Web: **роутер → Оборудование → Скачать аппаратный отчёт**. API владельца: `GET /api/v1/devices/{device_id}/hardware/report`. Передайте JSON через issue, указав версии OpenWrt/WrtMonitor и выполненные проверки. Android может экспортировать существующий диагностический отчёт из раздела системы; для аппаратной матрицы используйте аппаратный JSON Web/API, не придумывайте отсутствующую Android-кнопку.

Аппаратный JSON экспортирует только разрешённые model/board/target/CPU, датчики и пределы. В нём нет имени устройства, hostname, SSID, IP/MAC, сырых конфигураций, ключей, токенов и cookies. Нестандартные поля не пересылаются. Regression coverage: `test_public_report_privacy.py`. Пользовательские названия датчиков исключены. Поле модели необходимо для определения совместимости; если вы сами записали личные сведения в model/board, просмотрите эти значения перед публикацией.

Не публикуйте резервные копии, raw telemetry, системные журналы или приватный диагностический архив: это не обезличенный аппаратный отчёт.
